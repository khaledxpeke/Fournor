## 0. CONTEXT

`fournor.com` is the brand website for SATIA — ingredients, mixes and premixes for the
bakery and food-manufacturing sector. It is a showcase/catalogue site: brand, products,
expertise, news, franchises.

**Goal of this project:** the client must be able to add, edit, reorder and remove page
blocks, products, news items and promotional banners from a back-office, without a
developer touching code. The site must remain fast and fully indexable.

Organic search is this site's main acquisition channel. Any change that removes content
from the HTML source is a regression, regardless of how it looks in a browser.

# PHASE 1.5 — Build-time rendering + real i18n

**This phase does not involve Strapi.** It fixes the rendering architecture using the
content that already exists in `i18n.js`, `products.js` and `xp-data.js`.

## Why this phase exists

I reviewed the HTML generated by Phase 1. Most visible text is **absent from the
source** and injected at runtime by `i18n.js`:

```html
<a class="nav-link" href="/maison/" data-i18n="nav.maison"></a>   <!-- empty -->
<h2 data-i18n="news.title"></h2>                                   <!-- empty -->
<p data-i18n="footer.about"></p>                                   <!-- empty -->
<article class="p-card is-skeleton">...</article>                  <!-- no products -->
```

This is inherited from the old site, not introduced by you — but it is the single
biggest problem this project exists to fix. We fix it **before** introducing Strapi, so
that the rendering architecture is proven independently and Phase 3 becomes a pure
data-source swap rather than two risky changes at once.

## 1.5.1 — Three languages

The site is **FR / EN / AR** (there is a `data-lang="ar"` button, RTL handling, and
Amiri / IBM Plex Sans Arabic already loaded).

URL structure:

- French = default, **at the root**: `/solution/`, `/gamme/premix-poudres/`
- English: `/en/solution/`
- Arabic: `/ar/solution/`

**Do NOT move French under `/fr/`.** Those root URLs are already indexed by search
engines; changing them is pure risk with no benefit.

Astro i18n config: `defaultLocale: 'fr'`, `locales: ['fr','en','ar']`,
`prefixDefaultLocale: false`.

## 1.5.2 — All content renders at build time

Every text node must be present in the generated HTML, per locale. Remove the runtime
`data-i18n` filling mechanism — translations are read from the existing JS data files
at build time and passed into Astro components as props.

These **must** contain real text in the HTML source:

- All navigation links and every mega-menu entry (anchor text is a ranking signal)
- All `<h1>` / `<h2>` / `<h3>` headings
- All button and CTA labels
- The entire footer — about text, labels, address, phone label, expertise links
- The product carousel — real `<article>` cards, not `is-skeleton` placeholders
- The news section — real articles, not skeletons
- All `aria-label` values currently filled by `data-i18n-aria`

Skeleton placeholders may remain **only** for content genuinely loaded after user
interaction (e.g. live search results). Anything known at build time renders at build
time.

You may keep the `data-i18n` attributes in the markup if convenient, but they must no
longer be the mechanism that supplies the text.

## 1.5.3 — Language switching

- `<html lang>` and `dir="rtl"` for Arabic must be set in the **generated HTML**, not
  by the inline localStorage script.
- The language switcher **navigates to the equivalent URL** in the target locale. It
  must not swap content client-side.
- The inline localStorage script keeps at most a soft role: redirecting a first-time
  visitor to their preferred locale. It must never cause one URL to render different
  content — that breaks caching and is cloaking-adjacent.
- Every page needs a correct equivalent-URL mapping across all three locales, used by
  both the switcher and the hreflang tags.

## 1.5.4 — Head tags (currently missing entirely)

- `<link rel="canonical">` on every page, self-referencing, absolute URL
- `hreflang` alternates: `fr`, `en`, `ar`, plus `x-default` → the French URL
- Open Graph + Twitter card tags
- JSON-LD: `Organization` sitewide, `Product` on product pages, `NewsArticle` on news
- `@astrojs/sitemap`, including all three locales
- **Preserve the existing `<title>` and meta description values exactly.** Do not
  rewrite them. Translate for EN/AR only where translations already exist in `i18n.js`;
  report missing ones rather than inventing copy.

## 1.5.5 — Other

- Add a styled 404 page if there isn't one.
- **Report** where the contact form currently posts. A static build has no PHP handler,
  so it may already be broken. Do not implement a fix yet — just tell me what it does.
- Do not touch images or the image pipeline in this phase. Keep `<img>` as is.

**disable JavaScript in the browser and load the page.**

All navigation, headings, buttons, footer content, products and news must be visible

Also confirm: design and copy unchanged, no visual difference from Phase 1.

# PHASE 2 — Strapi 5

## 2.1 — Setup

- Create the Strapi 5 project in `cms/` using the official installer.
- SQLite is acceptable for local development, but the DB client must be read from
  environment variables so switching to MariaDB is config, not code.
- Production is **MariaDB 11.8.9** — `mysql` client, `utf8mb4` / `utf8mb4_unicode_ci`.
- Set the Strapi admin interface language to **French**.
- Document every variable in `cms/.env.example`.

## 2.2 — Content model

**Use the ZIP I am providing** (`src/api/**` and `src/components/**`). Unzip at the
Strapi project root. Do **not** recreate these through the admin UI.

It contains:

- **Collection types:** `Gamme`, `Produit`, `Actualité`, `Franchise`,
  `Bloc publicitaire`, `Page`
- **Single types:** `Accueil`, `Paramètres globaux`
- **Components:** `shared/` (seo, bouton, lien-social, lien-nav, element-texte) and
  `sections/` (hero, bandeau-defilant, image-texte, grille-ads, liste-produits,
  actualites-recentes, cta)

Each API folder includes its controller, service and route factory files.

**Enable the i18n plugin for `fr` (default), `en`, `ar` BEFORE entering any content.**
Localize: `Gamme`, `Produit`, `Actualité`, `Franchise`, `Page`, `Accueil`,
`Paramètres globaux`, and the `seo` component fields. For `Bloc publicitaire`, localize
`texteAlternatif` and `lien` only.

**Gap to fill:** the ZIP does not yet cover the **expertise / xp entries** or the
**ingredient families** revealed in Phase 1. Propose how to model them — likely a
dedicated collection type each, with the same `seo` component — and **show me the
proposal before implementing it**.

## 2.3 — The composability requirement (this is the point of the project)

`Accueil` and `Page` use a **dynamic zone** (`sections`) accepting any of the section
components in any order. The client must be able to add a block, reorder it, unpublish
it or delete it from the admin, with no code change. Verify this end to end.

Banners are `Bloc publicitaire` entries with `emplacement`, `ordre`, `actif`,
`dateDebut`, `dateFin`. The `grille-ads` section renders N active banners for a given
emplacement. The client never edits layout to change a banner.

## 2.4 — Media storage (critical)

Hostinger **overwrites the deployment directory on every redeploy**, so
`cms/public/uploads/` will be lost. `.gitignore` does not make files persistent.

- Install and configure `@strapi/provider-upload-cloudinary`.
- The provider must be **selected by environment variable**: local uploads for local
  development, Cloudinary when the Cloudinary variables are present. No code change to
  switch, no hardcoded provider.
- Configure `config/middlewares.js` security settings (CSP `img-src` / `media-src`) to
  allow the Cloudinary domain, or the admin preview will break.

**Scope — read carefully.** This applies **only** to media uploaded through the Strapi
admin. The existing static assets in `web/public/` (`banner.webp`, `logo-satia.webp`,
`ad-home-*.webp`, `expertise.webp`, `maison.webp`, `mix-intro.webp`, `maxi-graines.jpg`,
etc.) stay in the repository exactly where they are. Do **not** migrate them and do not
change how they are referenced.

## 2.5 — Seed the content, do not retype it

Write an **idempotent** seed script at `cms/scripts/seed.js` that reads `i18n.js`,
`products.js` and `xp-data.js` and creates Strapi entries **in all three locales**.

Coverage: the 4 gammes, the 10 products, the ingredient families, the xp/expertise
entries, global settings (menus, footer, contact details), and the homepage dynamic
zone reproducing the current homepage block by block.

Idempotent = safe to re-run without creating duplicates. I will run it again against
the production database later.

If EN or AR translations are incomplete in the source files, **report which keys are
missing** rather than inventing content.

The script must work with whichever upload provider is active.

## 2.6 — Access control

- A restricted **"Éditeur"** role: content CRUD only, no settings, no content-type
  builder.
- A **read-only API token** scoped to the content types the frontend consumes.

## 2.7 — Hostinger / Passenger compatibility (configure, do not deploy)

- `config/server.js` reads from env: `host: env('HOST','0.0.0.0')`,
  `port: env.int('PORT', 1337)`. **Never hardcode a port** — Passenger assigns it.
- Provide a Passenger-compatible **JS startup file** that boots Strapi
  programmatically. Use the **Strapi 5** programmatic API and cite the v5 docs — do not
  copy Strapi 4 syntax, which dominates older tutorials and will silently fail here.
- The admin panel must be buildable locally / in CI and deployed as a built artifact.
  It must **never** be built on the server — that build is the memory peak and Passenger
  will kill it.
- Every variable must be overridable from the environment; do not assume `.env` exists
  in production.
- **Do not use Strapi's cron plugin** — background workers are unsupported.
- **Verify the admin panel works without inbound WebSocket support.**

# PHASE 4 — Deployment wiring

**Do not write FTP or SSH deployment.** Hostinger already builds both projects from the
GitHub repo on push. Do not create deployment scripts that duplicate that.

1. Confirm the Astro build works from the `web/` subdirectory with Hostinger's build
   step (`npm run build`, output `dist`). Flag anything in the config that assumes the
   project sits at the repo root.
2. Confirm Strapi builds and starts from `cms/`, reading every setting from environment
   variables. Document in the README exactly which variables each of the two Hostinger
   apps needs.
3. **Publish → rebuild chain.** There is no Hostinger deploy hook, so it must be:
   ```
   Strapi webhook (entry publish/unpublish)
     → GitHub repository_dispatch (type: cms-publish)
     → workflow writes a build-stamp file and commits to the deployed branch
     → Hostinger rebuilds the frontend
   ```
   Make the webhook target URL and token **environment variables**, not hardcoded.
4. Add the same workflow on a **nightly cron**, so banners with `dateDebut` / `dateFin`
   go live on schedule without anyone publishing.
5. Never commit credentials, tokens or `.env` files.
